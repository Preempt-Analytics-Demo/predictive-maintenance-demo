# Learnings — How Our Way of Working Has Evolved

This is a running record of how we've collaborated with Claude on this capstone, and
what we learned along the way. It's grounded in what actually happened in this repo's
history, not just abstract principles — every claim below points at a commit.

---

## Timeline: how the process changed

**Phase 1 — No constitution yet (May 12–27).** The earliest commits show the normal
churn of exploratory work without shared rules: duplicate "Uninstalled gitleaks"
commits, merge conflicts in the EDA notebook resolved by just taking one side, files
added and later archived. Nothing was wrong with this — it's what early-stage,
figure-it-out work looks like — but it also meant every new Claude conversation
started from zero context and had to be steered from scratch.

**Phase 2 — The constitution doc (May 27–28).** `CLAUDE.md` was created
(`7f383c6`) the same day `api.py` and the simulator-FastAPI wiring went in — right
when the project stopped being "one script" and became multiple coupled components.
Two protocols were added almost immediately: **commit & push after every change**
(`6d4975a`), so work never sat un-integrated, and the **two-layer educational
comments law** (`374fde7`), which explicitly cites Redish (front-load the why) and
Krug (don't make the reader think) as the standard for code comments.

**Phase 3 — Rules written in response to real failures (June 30 – July 1).** This is
where the "constitution" stopped being aspirational and started being reactive to
specific incidents:
- **Runtime Dependency Check** (`eeda1df`) was added after code that shelled out to
  `git`/`dvc` worked locally but could silently fail inside a container missing that
  binary — a failure mode that wouldn't surface until the automated drift → retrain
  loop actually hit that code path in production.
- **Downstream Effects & Pre-Push Verification** (`9b02cc8`) was added the same day
  as a "virtual UXD/HCI panel audit" — five UX fixes generated by asking Claude to
  review the demo experience from a panel of expert personas — and it's the first
  rule that explicitly says "name every file, script, and workflow that consumes
  what you just changed," not just the one you edited.

**Phase 4 — Hardening the ML Ops loop itself (July 28–30).** After weeks of
automated retraining (dozens of `retrain: add N simulated observations` commits),
a real incident exposed a gap none of the existing rules caught: the training
data's baseline partition had been silently overwritten with synthetic rows,
inflating F1 to a suspicious 1.0. See the case study below — this is the strongest
evidence yet for why systems thinking has to be a standing habit, not a one-time
review. The same window closed with `9c6e31a`, which made the fixed pipeline's
model comparisons visible to any visitor via a committed `reports/model_leaderboard.md`
instead of MLflow's DagsHub UI, which is gated to repo contributors — turning the
incident's resolution into something the whole team could verify, not just whoever
fixed it.

## Our Learnings

### Prompt Engineering

- **Good scoping.** It's just as important to state what's *out* of scope as what
  we want. Leaving scope open invites Claude to "helpfully" touch adjacent code —
  the CLAUDE.md rule "Second Law — Elegant Sufficiency" exists specifically to push
  back on unrequested abstraction.
- **Aiming.** If you have enough domain knowledge, you can point the LLM at a
  specific, fruitful direction before it starts working, rather than leaving it to
  explore. All activity — AI or human — is bounded by attention: the more precisely
  you can aim before you "fire," the less course-correction you need afterward.
  Concretely on this project: naming the exact contract at risk (e.g. "this touches
  `feature_transformation.py`, check all three importers") gets a much more targeted
  response than "make sure nothing breaks."
- **Structuring the ask.** Naming a role, the task, the relevant context, and the
  expected output format up front gets a more targeted first draft than an
  open-ended request — the same reason CLAUDE.md's contract tables (`Symbol | What
  it controls | If changed without updating dependents`) work: the structure does
  the disambiguating instead of a back-and-forth.
- **Planning before building.** Sketching an approach first — and getting agreement
  on it — avoids the dead ends that come from committing to a design three files in.
  This matters most exactly where this project's biggest changes landed: the
  12-stage DVC pipeline (`fec6e60`), Docker containerization touching four coupled
  files at once (`ab8b4e2`), and the Gate 1 investigation that ultimately touched
  three separate files for one root cause (see the case study below) — all
  multi-file changes where committing to the wrong approach early is expensive to
  unwind.
- **Grounding with concrete examples.** Pointing at a specific number, commit, or
  error ("UDI 1–10000 should read 3.39% failure rate, it's reading 19.48%") produces
  a far more accurate fix than describing the symptom abstractly — this is what made
  the Gate 1 investigation tractable in the first place.
- **Providing assets.** A visual reference gives Claude something concrete to work
  from or explain against, instead of inventing structure from a text description
  alone. `images/Retraining Loop.png` and `reports/leaderboard_chart.png` are both
  visuals the README and leaderboard explain rather than replace.
- **Iterative fine-tuning.** Treat a prompt like an experiment: ship a first pass,
  look at what actually came back, adjust, repeat. The repeated "Krug/Redish pass"
  commits on the README (`8b046bb`, `672940b`, and others) are this pattern applied
  to documentation — each pass was a targeted correction based on what the previous
  pass actually produced, not a rewrite from scratch.

### AI Harness / Constitution Doc

An **AI Harness** is a wrapper of explicit rules around what the AI is — and isn't —
allowed to touch; `CLAUDE.md` is what that looks like concretely in this repo. Its
rules function as **SOPs (Standard Operating Procedures)**: not general advice, but
specific, repeatable procedures Claude follows the same way every time. We
introduced them because Claude kept repeating the same category of mistake across
sessions — a shared contract broken here, a downstream file forgotten there — and a
verbal correction in one conversation doesn't carry over to the next.

Writing project-specific rules into `CLAUDE.md` turned recurring verbal
course-correction into a standing, reusable contract. Each rule in the file maps to
an actual incident (see the timeline above) rather than being written speculatively:

| Rule | Added after |
|---|---|
| Commit & push protocol | Multi-component wiring made it easy to leave work un-integrated |
| Educational comments law | Need for future readers (including future Claude sessions) to understand *why*, not just *what* |
| Runtime dependency check | A container-only failure in the retrain loop that passed locally |
| Downstream effects / pre-push verification | A UX audit plus a pattern of small changes rippling into other components |

This is the single biggest lever we found: a well-scoped constitution doc saves
tokens and time versus re-explaining the same standards in every new Claude window,
and it turns tacit "things we've learned the hard way" into something a fresh
session can read on its own.

### Virtual Panel

Inspired by *Six Thinking Hats* — looking at the same problem from deliberately
different points of view — we used a virtual panel of domain-expert personas (e.g.
a UX/HCI panel, `9b02cc8`) to review a single artifact and surface issues no single
lens would catch. That audit alone produced five concrete fixes in one pass:
collapsing noisy script output to one summary line, adding phase headers to the
monitor, using relative paths so users could open report files directly, and
simplifying an error branch to one actionable instruction. The pattern generalizes:
pick personas whose blind spots don't overlap, run the same question past each, and
fold the feedback back into one change.

### Systems Thinking for ML Ops

A change in one part of an ML Ops pipeline can silently break a completely
different part, days or weeks later, with no error at the point the change was
made. Early on, Claude would make locally-correct changes without tracing where
else their effects would land. After we made "reason through downstream effects
before pushing" a standing rule, this improved noticeably — Claude began flagging,
unprompted, when a change to one component could have effects on another.

**Case study — the Gate 1 lock (2026-07-28 to 2026-07-30).** This is the clearest
example of why systems thinking has to be continuous, not a one-time checklist:

1. At some unknown point, the training data's baseline partition (UDI 1–10000,
   meant to be the untouched original AI4I dataset) was silently overwritten with
   synthetic simulator rows — failure rate drifted from the real 3.39% to 19.48%.
2. Because the corrupted partition was **easier** to fit, both registered models
   scored a suspiciously perfect F1 = 1.0.
3. The promotion logic (`promote_model.py`, "Gate 1") compared every new candidate
   against production with `new_f1 > prod_f1`. Once production sat at 1.0, nothing
   could ever score higher — so **every one of the 30 honest retrains since then
   was silently rejected**, including retrains on the eventually-fixed data.
4. Nothing in the existing rule set caught this, because no single change looked
   wrong in isolation: the data corruption, the gate's comparison logic, and the
   failure-injection method that fed the retrain loop were three separate files,
   each individually "correct."
5. The fix touched all three: restore the baseline partition from the verified CSV
   (`95f6ba2`), stop Gate 1 from treating a ≥0.999 production score as unbeatable
   (`0121bf7`), and fix the underlying PWF/OSF failure injector so future synthetic
   data has realistic variance instead of a signature so easy it could produce a
   fluke perfect score again (`ecb5c4c`). A regression test now fails loudly the
   moment the baseline partition's failure rate drifts (`26ad3dc`), so the next
   occurrence is caught automatically instead of requiring a human to notice a
   suspiciously perfect metric first.

**The takeaway:** a "perfect" score is a signal to distrust, not celebrate — and a
gate/threshold that assumes "higher is always better" needs an explicit ceiling
case. This is now folded into `CLAUDE.md`'s Gate 1 logic and is the kind of
cross-component invariant that only shows up if you're thinking about the system,
not the file.

### Documentation as a Living UX Surface

A quieter but persistent thread through the project's history: the README and
onboarding docs went through many iterative passes explicitly framed around
usability heuristics (Krug's "don't make me think," Redish's front-loading), adding
a glossary, primers before verbose output, and a single-keypress control panel to
replace memorized CLI flags. The lesson: for a demo whose audience includes
non-technical readers, documentation quality is not a one-off task — it needs the
same iterate-and-review treatment as code.

### Handover Documents

Documenting work as it happens — not reconstructing it after the fact — is what
lets the next session, human or Claude, pick up context without re-deriving it.
This shows up at two levels in the repo:

- **System-level track records, updated automatically.** `reports/monitor_log.jsonl`
  (one line per drift/retrain check, never overwritten) and
  `reports/promotion_log.jsonl` (one line per real model promotion, added in
  `9c6e31a`) are logs a human can `tail` or grep without reading any code to
  understand what happened.
- **Human-readable summaries built from those logs.** `9c6e31a` also added
  `reports/model_leaderboard.md`, generated from MLflow after every retrain and
  committed back to the repo — specifically because MLflow's own DagsHub UI is
  gated to repo contributors, so a teammate or demo visitor without an account had
  no way to see the same comparison `promote_model.py` was acting on. Turning a
  track record into a handover artifact means making it visible to whoever needs
  it next, not just to whoever generated it.
- **This document and `CLAUDE.md` itself** are the project-level version of the same
  idea: rather than re-explaining "why does the export script have a `--purge`
  flag" or "why did we change Gate 1" in every new conversation, the reasoning is
  written down once, and the next reader starts from it instead of from zero.

The common thread: a handover document is only as useful as how current it is. A
log updated automatically (the JSONL files) stays trustworthy by construction; a
doc updated manually (this one, `CLAUDE.md`) stays trustworthy only if updating it
is treated as part of finishing the work, not an optional extra step.

## Still Evolving

This doc should be updated the next time a new standing rule gets added to
`CLAUDE.md`, or the next time an incident teaches us something a rule didn't catch.

One direction we haven't tried yet: everything in `CLAUDE.md` today is scoped to
this one repo's contracts. A **global, user-level CLAUDE.md** — rules that are
project-agnostic (e.g. always check runtime deps before committing, always name
downstream consumers before touching a shared contract) — would let SOPs that
turned out to generalize travel with us into the next project instead of being
re-derived from scratch there too.
